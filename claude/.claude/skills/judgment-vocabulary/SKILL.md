# 판정 어휘 — 요구를 닫힌 어휘로 유형화하기

이 스킬이 다루는 일은 하나다. 산문으로 된 요구("CI 가 끝나면 머지", "세션이 코치 때문에 멈췄다", "새 export 에는 테스트가 있어야 한다")를 **코드가 분기하고 저장하고 비교하는 값의 체계**로 내리는 일이다. 이름을 잘 짓는 것이 목적이 아니다. 그 이름을 타입·런타임 검사·테스트·grep 이 집행하게 만드는 것이 목적이다. 이름만 맞춘 용어집은 한 번의 개명으로 무너지고, 집행되는 어휘는 개명을 견딘다.

이 방법은 세 산출물에서 같은 모양으로 반복됐다. 규칙 선언 엔진(관계·메커니즘을 닫은 선언 대수), 서비스 간 계약 패키지(공유 축·레코드·코드표), 여러 Git 호스트를 흡수하는 IR. 사례는 `references/worked-examples.md` 에 있다. 설계 중 막히면 거기서 같은 모양의 결정을 찾아라.

## 다섯 원리

### 1. 의미는 서로 파생하지 않는 작은 닫힌 축으로 쪼갠다

축은 한 질문에 대한 답의 닫힌 집합이다. 무엇에 대한 것인가(subject), 무슨 일이 일어났나(event), 어떻게 끝났나(outcome), 왜(reason), 누가(actor). 두 맥락이 같은 뜻으로 쓰는 낱말은 공유 축에 한 번 둔다.

복합 의미는 낱말을 이어 붙이지 않고 **축을 필드로 가진 레코드**로 만든다.

- `'session-started'` → `{ subject: 'session', event: 'started' }`
- `'pr-merge-failed-ci'` → `{ subject: 'change', event: 'refused', reason: 'checks-failed' }`

이어 붙인 문자열은 뿌리 낱말 하나를 바꿀 때 라벨·이벤트 이름·저장값을 줄줄이 끌고 간다. 레코드는 필드 하나만 바뀐다. 문자열을 파싱해 다시 축을 꺼내는 코드가 보이면 그 문자열이 원래 레코드였다는 신호다.

**문법.** 값의 품사를 고정하면 축의 정체가 드러난다. 누가 하는 일은 동사(`start`, `merge`, `settle`), 일어난 일·성립한 상태는 과거분사(`started`, `merged`, `refused`). 한 축 안에 품사가 섞이면 그 축에 두 질문이 섞인 것이다.

### 2. 판정에 쓰는 자리는 닫고, 관측에 쓰는 자리는 연다

코드가 분기하는 필드는 닫힌 유니언이다. 모르는 값은 거부한다. 기록만 하는 필드는 열린 형태로 둔다. 예를 들어 `{ kind: 'unknown', native: <원문> }` 처럼 원문을 보존한다.

한 맥락에서만 참인 낱말(`coached`, `superseded`)을 억지로 공유 축에 넣지 마라. 그 맥락의 어휘에 두고, 두 번째 맥락이 같은 뜻으로 쓰기 시작할 때 승격한다. 가장 가까운 축에 눌러 넣으면 그 축의 다른 값과 뜻이 겹친다.

### 3. 철자는 경계에서만, 한 방향으로, 단사로 만든다

경계는 저장소, 외부 API, HTTP, 화면, 다른 호스트다. 내부는 개념(축 값·레코드)으로만 말하고, 바깥 철자는 경계마다 하나인 코드표가 만든다.

- 손으로 쓰는 방향은 개념 → 코드 하나다. 역표는 기계가 만든다.
- 코드표는 생성 시점에 충돌을 거부한다(두 개념이 같은 코드로 가면 throw).
- 저장 코드는 한 번 쓰면 동결한다. 개념의 이름이 바뀌어도 저장 코드는 그대로 두고, 코드표에서만 매핑을 바꾼다.
- 외부 시스템 고유의 철자(`Resolves #N`, 서명 헤더 이름, 필드명)는 어댑터의 코드표 안에만 산다. 코어는 의도(`propose`, `merge`, `settle`)만 말한다.

### 4. 판정하지 못한 것은 통과가 아니다

판정 결과는 최소 세 값이다. `upheld`(지켰다), `violated`(어겼다, 반례 목록 동반), `unjudged`(판정하지 못했다, 이유 동반). 두 값으로 접는 순간 "데이터가 없음"이 "문제가 없음"으로 읽힌다. 실제로 터진 형태는 이렇다. CI 보고 0 건을 `none` 으로 읽고, 게이트가 `none` 을 통과로 처리해 검사 없이 머지됐다.

표현하지 못하는 나머지에 이름을 붙여라.

- 표현할 수 없는 규칙 → `draft` 로 등록. 버리지도, 비슷한 규칙으로 근사하지도 않는다.
- 판정 대상이 없어 건너뜀 → `skipped`. `passed` 와 다른 값이다.
- 어댑터가 지원하지 않는 의도 → `capability` 로 미리 선언하고, 호출 시 거절 사유를 돌려준다.
- 알 수 없는 외부 값 → `unknown` + 원문. 판정에 쓰지 않는다.

판정은 한 자리에서 한다(`judge = relate ∘ extract`). 관측 기록(저널·로그)은 판정하지 않는다. 판정 결과는 boolean 이 아니라 **위반 원소 목록**이다. 목록이 있어야 사람과 모델이 무엇을 고칠지 안다.

### 5. 어휘 자체를 반증 가능한 가설로 운영한다

축 하나, 코드표 하나를 정할 때마다 **이 결정이 틀렸다는 신호**를 함께 적는다.

- "같은 뜻을 내는 레코드가 둘 이상 생기면 축 분해가 틀렸다."
- "새 호스트를 붙이는데 코어를 고쳐야 했다면 그 개념은 축이 아니었다."
- "코어에서 호스트 이름 grep 이 0 건이 아니면 경계가 샌다."

신호는 grep·테스트·커버리지 표처럼 기계로 셀 수 있는 형태가 좋다. 측정이 결정을 뒤집으면 값을 지운다. 값이 많다는 것은 자산이 아니다. 닫혀 있고, 진화 규칙이 있다는 성질이 자산이다.

## 절차

요구나 기존 코드가 주어지면 다음 순서로 진행한다. 큰 변경이면 각 단계를 사용자에게 보여주고 다음으로 간다.

1. **판정 지점 찾기.** 이 요구에서 코드가 분기·저장·비교하는 자리를 나열한다. 분기하지 않는 낱말은 이 스킬의 대상이 아니다(용어집에 둔다).
2. **철자 수집.** 같은 개념의 현재 철자를 모두 모은다. 코드 리터럴, 저장값, 외부 API 필드, 화면 문구, 로그. 같은 뜻에 철자 둘, 철자 하나에 뜻 둘인 곳을 표시한다.
3. **질문으로 축 세우기.** 각 값이 어떤 질문에 답하는지 묻는다. 한 값이 두 질문에 답하면 레코드로 쪼갠다. 기존 축이 있으면(`CONTEXT.md`, 계약 패키지, ADR) 먼저 읽고 기존 낱말을 재사용한다. 새 축은 마지막 수단이다.
4. **이질적 대상이면 갈림 축 표.** 여러 호스트·공급자를 흡수하는 IR 이라면 대상을 하나씩 기술하지 말고 **대상을 가르는 축을 행으로** 세운다(인증 방식, 이벤트 전달, 머지 의미, 검사 보고 방식…). 각 칸이 IR 의 required / extensible / capability 중 어디에 떨어지는지 정한다.
5. **공백 이름 붙이기.** 각 판정 지점마다 "데이터가 없을 때 무엇이 되는가"를 적는다. 답이 기존 값 중 하나(특히 성공·통과)로 접히면 결함이다.
6. **경계 코드표.** 경계마다 개념 → 코드 표를 하나 쓰고, 충돌 검사와 왕복 테스트(개념 → 코드 → 개념)를 붙인다. 저장 코드는 동결 대상임을 표시한다.
7. **반증 신호 기록.** 결정마다 뒤집기 신호를 ADR 이나 계약 주석에 남긴다.
8. **집행.** 타입(닫힌 유니언, 완전 매칭), 런타임 검사(코드표 생성 시 throw, 모르는 이름 거부), 테스트(왕복, 공백), grep 규칙 중 무엇이 각 원리를 지키는지 정한다. 집행되지 않는 규칙은 다음 개명에서 깨진다.

## 결함 모양 (리뷰할 때 찾을 것)

| 모양 | 예 | 고치는 방향 |
|---|---|---|
| 낱말 이어 붙이기 | `` `${role}-retry` ``, `` `not-${OUTCOME.succeeded}` `` | 레코드 필드로 분리 (`{ role, attempt }`), 부정 값은 축에 따로 둔 값으로 |
| 같은 뜻 두 철자 | 이슈 이벤트 `stopped/resumed` 와 IR `closed/reopened` | 한 축에 하나, 나머지는 경계 코드표로 |
| 한 철자 두 뜻 | 상태 축 값 `closed` 를 사유 자리에도 씀 | 질문별로 다른 축 |
| 공백이 성공으로 접힘 | 보고 0 건 → `none` → 통과 | `unjudged` / `pending` 분리 |
| 경계 철자가 코어에 샘 | 코어에서 `X-Gitea-Signature` 참조 | 어댑터 코드표로 이동, grep 0 건을 완료 조건으로 |
| boolean 판정 | `isValid(): boolean` | 위반 원소 목록 반환 |
| 손으로 쓴 양방향 표 | 정방향·역방향 맵을 따로 유지 | 정방향만 쓰고 역표는 생성 |
| 문서와 계약 불일치 | 문서의 값 목록과 계약 코드가 다름 | 계약을 정본으로, 문서는 계약을 인용 |

## 이 방법이 주장할 수 있는 것과 없는 것

이 절차가 확실히 하는 일은 **실패를 관측 가능하게** 만드는 것이다. 개명이 어디까지 번지는지, 무엇이 판정되지 않았는지, 어떤 어댑터가 무엇을 못 하는지가 값으로 드러난다. 이것이 코드 품질이나 에이전트 성공률을 올린다는 주장은 측정 없이 하지 마라. 산문을 축 좌표로 내리는 분류 단계는 사람이 하든 모델이 하든 틀릴 수 있다. 중요한 분류는 사용자에게 확인받고, 가능하면 양성·음성 예시로 검증한다.

## 산출물

작업 크기에 맞게 다음 중 필요한 것만 만든다.

- 축·레코드 정의(계약 모듈 또는 타입 파일)
- 경계별 코드표와 왕복·충돌 테스트
- 공백 표: 판정 지점 × "데이터 없음일 때의 값"
- 갈림 축 표(IR 일 때)
- 결정마다 뒤집기 신호를 단 ADR 또는 `CONTEXT.md` 항목 (형식은 domain-modeling 스킬을 따른다)
- 리뷰라면 위 결함 모양 표의 행 단위 지적, 각 지적에 파일 경로와 고치는 방향
