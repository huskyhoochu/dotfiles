# PRD 작성 — "그래서 뭘 하라는 건데?"에 즉답하는 문서

핵심 철학: **PRD는 서사가 아니라 디렉팅이다.** 독자는 두 부류다 — 훑는 사람(frontmatter와 §0만 읽는다)과 실행하는 사람(§2와 §3을 따라간다). 히스토리 회상, 구 명칭, 의미 없는 표기는 둘 모두에게 소음이다. 아래 원칙은 그 소음을 구조적으로 차단한다.

기존 문서군을 손볼 때는 먼저 그 프로젝트의 규약 문서(예: `_docs/prd/README*.md`)가 있는지 확인하고, 있으면 그것이 이 스킬보다 우선한다. 없으면 이 스킬의 골격을 제안하고 규약 문서로 남겨라.

## 1. Frontmatter — 본문 읽기 전에 5줄 안에 파악되게

모든 PRD 최상단에 YAML frontmatter를 둔다. 목적은 "누가, 무엇을, 어디를, 언제 할 수 있는지"를 스캔 가능하게 만드는 것이다.

```yaml
---
title: 본문 h1과 일치하는 짧은 제목
description: 한 줄 — 무엇을 왜 하는가
type: umbrella | plan | ticket | reference
status: todo | blocked | in-progress | partial-done | on-hold
author: 주 담당자 이름 (부 담당은 본문 티켓 대응 표기로)
difficulty: easy | medium | hard | n/a   # easy=수용 기준이 명세돼 기계적 검증 가능 / hard=설계 결정 동반 / n/a=umbrella·plan
scope_repos: [기본 리포]                  # 타 리포 작업 동반 여부가 여기서 드러나야 한다
scope_paths:                              # "수정할 곳"만 — 참조만 하는 경로는 넣지 않는다
  - path/   # 짧은 사유 주석
  - "다른리포: path"
blocked_by: 실질 블로커만 (없으면 null)
updated: YYYY-MM-DD
---
```

- **blocked_by에 당연한 전제를 쓰지 마라.** "미팅 이후", "승인 후"는 모든 티켓의 전제라 정보가 0이다. 실측 의존, 타 티켓 의존, 미결 설계 질문처럼 그 티켓 고유의 조건만 쓴다.
- frontmatter는 요약이지 SSOT가 아니다 — 본문과 어긋나면 본문이 이기고, 발견 즉시 frontmatter를 고친다.

## 2. 파일명이 메타데이터다

파일 목록만 훑어도 문서군의 구조가 보여야 한다.

- **공통 prefix는 간결하게.** 문서군 이름이 길면 줄여라 (예: `tool-discrimination-` → `toolgate-`). prefix가 자기 설명적이면 8자 안팎이 이상적이다.
- **주 담당을 접미로** (예: `...-han.ko.md`, `...-funes.ko.md`). 파일명만으로 "내 일인가"가 판별된다.
- **정렬 문자(a, b, c…)를 쓰려면 그 의미를 규약으로 명시하라.** 의존성인지, 소유자 블록 인덱스인지, 단순 작성 순서인지. 의미 없는 체계는 재배열 요구를 부른다 — 만들지 마라. 소유자 블록(예: a–c = 담당자 A, d–f = 담당자 B)이 실전에서 가장 스캔하기 좋다.
- **본문 프로즈에서 파일 문자를 참조하지 마라 — 티켓 번호로 참조하라.** 문자는 재배열될 수 있는 라벨이고, 티켓 번호는 안정 식별자다. 이 분리를 지키면 파일명을 바꿔도 본문이 깨지지 않는다.
- **결번은 재사용하지 않는다.** 흡수·폐기된 티켓 번호는 지도에 "결번(X에 흡수)"으로 명시한다.

## 3. 표준 챕터 골격 — ticket 문서는 고정, §0이 전부다

```
## 0. 디렉팅 — 그래서 뭘 하면 되나
## 1. 왜 — 배경·문제
## 2. 무엇을 — 작업 항목          (하위 절 2-a, 2-b… 허용. 스펙·분기·산출물 표는 여기로)
## 3. 끝났다의 기준 — 수용 기준    (체크박스)
## 4. 순서·의존
## 5. 리스크·유의
```

- **§0은 명령형 3~5줄 + "끝의 정의" 한 줄.** 각 줄에 담당을 괄호로 박는다: `1. **(A, 지금)** …을 한다`, `2. **(B, X 실측 뒤)** …`. §0만 읽고 착수할 수 있어야 한다 — 이것이 이 스킬의 존재 이유다.
- **§3 수용 기준은 검증 가능하게.** "grep으로 0건 확인", "테스트로 고정", "재실행 시 결정론적으로 동일" 같은 기계 검증 문구를 선호하라. fail 방향(실패 시 안전한 쪽으로 떨어지는가) 검증을 포함할 수 있으면 포함한다.
- 결정이 아직 없는 티켓이면 §2에 "설계 입력(결정할 질문 목록)"과 "구현 스펙(자리 표시 — 결정 뒤 작성)"을 분리해 둔다. **결정을 문서가 선점하지 마라** — 미결은 "결정 대기 + 결정 소유자"로 표기한다.
- h1 아래 메타 줄(작성일·티켓 대응·집행 원칙)은 자유 형식이되 챕터 번호를 차지하지 않는다.

umbrella/plan 문서는 골격이 자유지만 §5의 지도·다이어그램은 필수다.

## 4. 현재 시점 서술 — 히스토리는 changelog에만

살아있는 문서는 **지금 무엇이 참이고 무엇을 해야 하는지**만 말한다.

- "구 X였는데 Y로 바뀜" → **"Y다"**. 뒤집힌 결정, 구판 내용, 부존재하는 파일·티켓·경로를 본문에서 회상하지 않는다.
- "○월 ○일 실측 결과…", "△△ 시점 결정이 뒤집혀…" 같은 날짜 서사를 본문에서 걷어낸다. 단, **데이터의 유효기간 한정은 히스토리가 아니라 현재 사실이다** — "착수 시 재실측 필요", "현재 dev에 잔존"은 유지한다.
- 변경 이력이 필요하면 문서 말미의 전용 절(`## 문서 정리 기록 (changelog — 본문은 현재 시점 기준, 이력은 여기에만)`)에만 쓴다.
- **코드 경로·패키지명은 현행 명칭만.** 리팩터·rename 이후의 구 명칭 병기는 금지 — 구→신 매핑이 필요하면 changelog나 우산 문서의 완료 기록 한 곳만 가리킨다.
- 참조하는 파일·링크는 전부 실재해야 한다(self-contained). 문서군을 일괄 rename했다면 grep으로 깨진 링크를 반드시 검증하라 — 기계적 치환은 존재하지 않는 파일명을 만들어낸다.

## 5. 포함·의존의 시각화 — 티켓 지도와 다이어그램

티켓이 여러 문서에 흩어지는 순간 "X는 어디 있지?"가 생긴다. plan/umbrella 문서에 둘 다 둔다:

1. **티켓 전체 지도 (표)** — 모든 티켓이 정확히 한 "집" 문서를 가진다:

   | 티켓 | 내용 | 담당 | 상세 문서 | 선행 조건 |
   |---|---|---|---|---|

2. **의존 다이어그램 (ASCII)** — 문서 = 티켓의 집으로 묶고, 화살표 = "왼쪽이 끝나야 오른쪽이 진행된다". 독립 착수 가능한 것은 별도 줄로 빼고 "무엇만 무엇을 기다리는지"를 짧게 단다.

의존 정보의 원본은 frontmatter `blocked_by` + 각 문서 §4이고, 지도·다이어그램은 그 집계다 — 어긋나면 원본을 고친다.

## 6. 스멜 → 행동

문서를 다듬다가 아래를 만나면 문서 수정으로 끝내지 말고 지적하거나 티켓으로 승격하라:

- **역할 설명 표가 필요해진다** ("이 세 파일은 사실 역할이 달라요") → 구조 자체가 복잡하다는 신호. 설명 표는 임시 조치로 두되, **구조 단순화 티켓을 제안**한다. 원본이 하나면 표가 필요 없다.
- **히스토리 없이 설명이 안 된다** → 현재 구조가 서사에 기대고 있다는 신호. 재작성 대상.
- **구현이 완료된 PRD** → 삭제한다. 잔존 정보(교훈·후속 백로그)만 우산 문서의 DONE 절로 이관하고 참조를 갱신한다.
- **frontmatter와 본문의 담당·상태 불일치** → 본문 기준으로 frontmatter를 고친다.

## 7. 마무리 점검 (제출 전 셀프 체크)

- [ ] frontmatter 5줄 스캔으로 누가/무엇을/어디를/언제가 나오는가?
- [ ] §0만 읽고 첫 행동을 시작할 수 있는가? 각 줄에 담당이 있는가?
- [ ] grep 검증: 구 명칭·결번 티켓·깨진 파일 링크 0건, 전 ticket 문서의 챕터 골격 동일.
- [ ] 본문에 히스토리 서사가 없는가? (changelog 절 제외)
- [ ] 모든 티켓이 지도 표에 있고, 집 문서가 하나씩인가?
- [ ] 한국어 문서라면 윤문 1회(번역투·겹말·주어 반복·레지스터 혼용 점검) 후 제출.
