# PRD 작성

PRD는 서사가 아니라 디렉팅이다. 독자는 둘이다. 훑는 사람은 frontmatter와 §0만 읽고, 실행하는 사람은 §2와 §3을 따라간다. 이 스킬은 네 출처를 한 절차로 엮는다.

| 출처 | 맡는 일 |
|---|---|
| [OKF v0.2](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md) (Google Cloud) | 문서 형식. frontmatter, 신뢰·수명 신호, index.md·log.md |
| 1원칙 사고 (Musk 5단계) | 요구 거르기. 이름 → 의심 → 삭제 → 단순화 → 가속 → 자동화 |
| *Tidy First?* (Kent Beck) | 작업 쪼개기. [구조]·[동작] 분리, First·After·Later 배치 |
| *Code Complete* 2판 9장 (McConnell) | 설계 깊이. 한 문장 요약 → 의도 수준 의사 코드 → 코드 주석 |

프로젝트에 PRD 규약 문서(예: `_docs/prd/README*.md`)가 있으면 그것이 이 스킬보다 우선한다. 없으면 이 스킬의 골격을 제안하고 규약으로 남긴다.

## 1. 쓰는 순서

문서는 §0부터 읽히지만 쓰는 순서는 PPP가 루틴을 만드는 순서를 따른다. 한 단계가 막히면 다음으로 넘어가지 말고 앞 단계로 돌아간다.

1. **전제 확인.** "지금 코드는 X를 한다"는 주장을 최신 기본 브랜치(pull 후)에서 grep으로 확인하고 기준 커밋을 적는다. 다른 리포의 주장은 그 리포의 최신 브랜치로 확인한다. 이 작업을 실제로 요구한 사람이 있는지도 여기서 본다.
2. **근본 사실.** 티켓의 끝 목표와 그 목표에 꼭 필요한 것을 한두 문장으로 적는다.
3. **요구 거르기.** §3의 1원칙 절차로 §2-a 요구 검증표를 만든다.
4. **`description` 한 문장.** 한 문장으로 안 써지면 티켓 범위가 흐린 것이다. 2로 돌아간다.
5. **수용 기준.** 설계보다 먼저 어떻게 검증할지 정한다.
6. **설계.** §2를 쓰고, 필요하면 §5의 의사 코드를 둔다.
7. **§0 디렉팅.** 2~6의 결과를 실행 순서대로 접는다.
8. **번들 갱신.** frontmatter, `index.md`, `log.md`를 고치고 §8 셀프 체크를 한다.

## 2. 문서 형식 — OKF v0.2

PRD 디렉터리(`_docs/prd/` 등)는 OKF 번들 하나이고, PRD 한 편은 OKF 개념 문서 하나다. OKF가 정한 키는 OKF 뜻 그대로 쓰고, PRD에만 필요한 키는 OKF가 허용하는 확장 키로 둔다.

```yaml
---
# OKF 키
type: PRD Ticket                  # 필수. PRD Umbrella | PRD Plan | PRD Ticket | Reference
title: 본문 h1과 같은 짧은 제목
description: 무엇을 왜 하는지 한 문장
tags: [sync, polling]
status: draft                     # draft | stable | deprecated — 문서 수명
generated: { by: human:funes, at: 2026-10-08T14:00:00+09:00 }
verified: { by: human:han, at: 2026-10-09T10:00:00+09:00 }   # 결정 소유자 검토 뒤에만
stale_after: 2026-11-01T00:00:00+09:00                        # 실측값이 있을 때만
sources:
  - id: han-1007                  # 본문 각주 [^han-1007]의 라벨
    resource: /meetings/2026-10-07.md
    title: han·funes 미팅
    author: human:han
# PRD 확장 키
owner: human:jihoon               # 주 담당. 부 담당은 §0 줄마다 적는다
progress: todo                    # todo | blocked | in-progress | partial-done | on-hold
difficulty: medium                # easy=수용 기준만으로 기계 검증 / hard=설계 결정 동반 / n/a=umbrella·plan
scope_repos: [sync-app]           # 다른 리포 작업이 있으면 여기서 드러난다
scope_paths:                      # 수정할 곳만. 참조만 하는 경로는 넣지 않는다
  - packages/sync-core/src/       # 짧은 사유
blocked_by: null                  # 실질 블로커만
---
```

- **`status`는 문서 수명, `progress`는 작업 진행이다.** 한 키에 섞지 않는다. 초안은 `draft`이고, 결정 소유자가 검토하면 `verified`를 적고 `stable`로 올린다. 그러면 OKF 신뢰 등급이 human-reviewed가 된다.
- **행위자 표기.** 사람은 `human:<id>`, 에이전트는 `<producer>/<version>`(예: `claude-code/claude-opus-5-5`), 자동 처리는 `process:<id>`로 쓴다. 에이전트가 쓴 초안은 `generated.by`를 에이전트로 적는다.
- 시각은 UTC 오프셋을 붙인 ISO 8601로 쓴다.
- **`blocked_by`에 당연한 전제를 쓰지 않는다.** "미팅 이후", "승인 후"는 모든 티켓의 전제라 정보가 없다. 실측 의존, 다른 티켓 의존, 미결 설계 질문만 쓴다.
- **`stale_after`는 데이터의 유효기간이다.** "착수 시 재실측 필요"는 히스토리가 아니라 현재 사실이므로 그 시각을 여기에 적는다.
- **근거는 `sources`와 각주로 단다.** 본문 주장의 근거는 `sources[].id`를 라벨로 한 각주(`[^han-1007]`)로 붙인다. 순번이 아니라 id로 걸기 때문에 목록 순서를 바꿔도 근거가 어긋나지 않는다.
- frontmatter는 요약이다. 본문과 어긋나면 본문이 맞고, 발견한 즉시 frontmatter를 고친다.

### 번들 파일

```
_docs/prd/
  index.md                     # frontmatter 없음(번들 루트만 okf_version: "0.2")
  log.md                       # 변경 이력. "## YYYY-MM-DD" 묶음, 최신이 위
  <prefix>-<주제>-<담당>.ko.md
```

- `index.md`는 섹션 제목 아래 `* [제목](/경로.md) - description` 줄로 문서를 나열한다.
- 링크는 번들 루트 기준 절대 경로(`/...`)로 쓴다. OKF 소비자는 깨진 링크를 허용하지만, PRD의 링크는 모두 실재해야 한다. 일괄 rename 뒤에는 깨진 링크를 grep으로 확인한다.

### 파일명이 메타데이터다

- **공통 prefix는 8자 안팎으로 짧게** 쓴다(`tool-discrimination-` → `toolgate-`).
- **주 담당을 접미로** 붙인다(`…-han.ko.md`). 파일명만 보고 내 일인지 판별할 수 있어야 한다.
- **정렬 문자(a, b, c…)를 쓰려면** 의존 순서인지, 소유자 블록인지, 작성 순서인지 그 뜻을 규약에 적는다. 뜻 없는 정렬 체계는 만들지 않는다. 실전에서는 소유자 블록(a–c = A, d–f = B)이 가장 훑기 쉽다.
- **본문은 파일 문자가 아니라 티켓 번호로 참조한다.** 문자는 바뀌는 라벨이고 번호는 안정 식별자다.
- **결번은 재사용하지 않는다.** 흡수·폐기된 번호는 지도에 "결번(X에 흡수)"으로 적는다.

## 3. 요구 거르기 — 1원칙 사고

Musk 5단계의 순서(의심 → 삭제 → 단순화 → 가속 → 자동화)를 그대로 지킨다. 방법의 근거와 선례는 polydeukes 위키 `foundation.research.first-principles-prd.md`에 있다.

- **요구마다 요구한 사람의 이름을 적는다.** "미팅 결정", "팀 합의", "법무팀"은 부서명과 같아서 의심할 상대가 보이지 않는다. 이름을 댈 수 없으면 "확인되지 않음 + 결정 대기(소유자)"로 내린다.
- **근본 사실이 필요로 하지 않는 요구는 지운다.** "기존 코드를 건드리지 않으려고"는 요구자가 아니다.
- **지운 뒤에 단순화한다.** 살아남은 요구만 다듬는다.
- **지운 것의 일부를 뒤 티켓이 되살리는 것이 정상이다.** 되살린 것이 없으면 덜 지운 것이다.
- **의심하는 대상은 요구이고, 측정된 사실은 의심하지 않는다.** 실패하는 테스트, 다른 패키지의 import는 지울 수 없다. 그 사실을 근거로 요구를 지운다.
- **이미 있는 것은 요구가 아니다.** 코드에 이미 구현됐거나 표준 라이브러리로 되는 것은 §1 배경에 현재 사실로 적는다.
- **자동화는 마지막이다.** AI 자동화·일괄 처리 티켓은 같은 흐름의 수동 티켓이 자리 잡은 뒤에 둔다. 기술적으로 독립이어도 지도에 "우선순위는 X 뒤"를 적는다.

결과는 §2-a 요구 검증표 하나로 남긴다. 표 위에 근본 사실을 쓰고, 열은 요구와 요구한 사람 둘이다. 요구한 사람 칸에는 행위자(`human:han`)를 쓰고, 회의록·로드맵 행 같은 근거 산출물이 있으면 각주를 단다. 표에는 이 티켓이 **하는** 요구만 남긴다. 삭제·제외한 요구는 umbrella/plan 문서의 "하지 않는 것" 표(하지 않는 것 | 이유·대신 | 관련 티켓) 한 곳에 모은다.

## 4. 작업 쪼개기 — Tidy First

- **코드 티켓의 §0 각 줄은 `[구조]`와 `[동작]` 중 하나다.** `[구조]`는 동작이 그대로인 정리(함수 추출, 공유 상수 분리, 현재 동작을 고정하는 테스트)이고, `[동작]`은 사용자가 겪는 결과가 바뀌는 변경이다. 한 줄은 한 커밋(또는 PR)이고, 한 줄에 둘을 섞지 않는다. 결정·조사 줄에는 표기하지 않는다.
- **정리처럼 보여도 `[동작]`인 변경이 있다.** 기존에 받던 입력을 거부하게 되는 변경(검사 강화, 변환 제거)이 그렇다.
- **배치.** 다음 `[동작]`을 쉽게 만드는 정리만 앞(First)에 둔다. 동작 변경으로 쓰이지 않게 된 코드의 삭제는 뒤(After)에 둔다. 지금 필요 없는 정리는 plan 문서의 "문서군 밖" 목록(Later)으로 보낸다.
- **되돌릴 수 있는가로 확인 장치의 두께를 정한다.** `[구조]`는 대개 되돌릴 수 있고 `[동작]`은 대개 되돌릴 수 없다. 되돌릴 수 없는 동작 변경(고객 파일 덮어쓰기, 기존 데이터 거부, 외부 전송)에는 확인 화면·사전 조회·동의를 두고 §2에 그 이유를 적는다. 되돌리기 쉬운 변경에는 장치를 더하지 않는다.
- §3에 "`[구조]` 커밋에서 기존 테스트가 고치지 않고 통과한다"를 넣는다.

## 5. 설계 깊이 — 의사 코드 프로그래밍 과정(PPP)

분기·오류 처리가 있는 `[동작]` 줄, 또는 `difficulty: hard` 티켓에는 §2-b 의사 코드를 둔다. 접근자나 단순 전달처럼 뻔한 변경에는 두지 않는다. 결정이 아직 없으면 의사 코드도 쓰지 않는다(§6).

1. **문제 정의를 먼저 적는다.** 입력, 출력, 숨기는 정보, 사전 조건, 사후 조건을 쓴다.
2. **이름을 짓는다.** 이름이 흐리면 설계가 흐린 것이다. 이름을 또렷하게 고칠 수 없으면 설계로 돌아간다.
3. **의도 수준으로 쓴다.** 대상 언어의 문법(`malloc`, `*ptr`, `return 1`)을 쓰지 않는다. 동시에 코드로 옮기는 일이 거의 기계적일 만큼 낮은 수준까지 내린다. 한 줄이 코드 2~10줄로 펼쳐지는 정도가 기준이다.
4. **오류 처리를 넣는다.** 잘못된 입력, 다른 루틴의 잘못된 반환을 다루는 줄을 의사 코드에 둔다.
5. **대안은 의사 코드 단계에서 시험한다.** 가장 나은 것만 남긴다. 코드를 쓰기 시작한 뒤에는 나쁜 설계도 버리기 어렵다.
6. **결정 소유자가 의사 코드를 검토한다.** 검토가 끝나면 `verified`를 적는다. 코드 35줄보다 의사 코드 11줄이 리뷰하기 쉽다.
7. **구현할 때 의사 코드 줄을 코드 주석으로 옮긴다.** 그래서 구현이 끝난 PRD를 지워도 설계 의도는 코드에 남는다.

```
§2-b resolveConflict — 충돌한 두 레코드 중 채택할 것을 정한다
입력: 로컬 레코드, 서버 레코드 / 출력: 채택 레코드, 판정 사유
사전 조건: 두 레코드의 id가 같다 / 사후 조건: 사유는 정해진 값 중 하나다

  판정 사유의 기본값을 "판정 불가"로 둔다
  두 레코드의 버전이 같으면 서버 레코드를 채택하고 "동일"로 판정한다
  한쪽 버전이 더 높으면 그쪽을 채택하고 "최신 우선"으로 판정한다
  버전을 읽을 수 없으면 아무것도 채택하지 않고 "판정 불가"를 돌려준다
```

## 6. 문서 골격

ticket 문서의 골격은 고정이다.

```
# <title>
## 0. 디렉팅 (세 줄 요약)
## 1. 왜 (배경·문제)
## 2. 무엇을 (작업 항목)      2-a 요구 검증표 · 2-b 의사 코드(필요할 때) · 2-c… 스펙·분기·산출물
## 3. 끝났다의 기준 (수용 기준)
## 4. 순서·의존
## 5. 리스크·유의
```

- **§0은 명령형 세 줄이 기본이고 다섯 줄이 상한이다.** 여기에 "끝의 정의" 한 줄을 붙인다. 각 줄에 주체와 시점을 괄호로 적는다. 예: `1. **(jihoon, 지금)** [구조] …`, `2. **(minseo, 1 뒤)** …`. 담당자가 한 사람뿐인 문서군이면 주체는 저장소다(`(electron, 지금)`). §0만 읽고 착수할 수 있어야 한다. §0 줄은 의도 수준으로 쓰고, 파일·함수 이름은 §2에 둔다.
- **§3 수용 기준은 체크박스로 쓴다.** "grep으로 0건", "테스트로 고정", "재실행 시 결정론적으로 동일" 같은 기계 검증 문구를 쓰고, 실패하면 안전한 쪽으로 떨어지는지를 검증할 수 있으면 넣는다.
- **결정이 없는 티켓은 결정을 선점하지 않는다.** §2를 "설계 입력(결정할 질문 목록)"과 "구현 스펙(결정 뒤 작성)"으로 나눈다. 미결은 "결정 대기 + 결정 소유자"로 쓰고 `status: draft`로 둔다.
- 메타 정보는 frontmatter에만 둔다. h1 아래에 메타 줄을 따로 두지 않는다.

umbrella/plan 문서는 골격이 자유다. 단 맨 위 절은 다음 둘이다.

1. **티켓 지도(표).** 모든 티켓은 정확히 한 "집" 문서를 가진다.

   | 티켓 | 내용 | 담당 | 상세 문서 | 선행 조건 |
   |---|---|---|---|---|

2. **의존 다이어그램(ASCII).** 문서를 티켓의 집으로 묶는다. 화살표는 "왼쪽이 끝나야 오른쪽이 진행된다"는 뜻이다. 독립 착수할 수 있는 것은 별도 줄로 빼고, 무엇이 무엇을 기다리는지 짧게 단다.

의존 정보의 원본은 각 문서의 `blocked_by`와 §4이고, 지도와 다이어그램은 그 집계다. 서로 어긋나면 원본을 고친다. "하지 않는 것" 표와 "문서군 밖(Later)" 목록도 umbrella/plan 문서에만 둔다.

## 7. 현재 시점 서술과 스멜

본문은 지금 무엇이 참이고 무엇을 해야 하는지만 말한다. 이력은 `log.md`에만 쓴다.

- "구 X였는데 Y로 바뀜"은 "Y다"로 쓴다. 뒤집힌 결정, 구판 내용, 없는 파일·티켓·경로를 본문에서 회상하지 않는다.
- 날짜 서사("○월 ○일 실측 결과…", "△△ 결정이 뒤집혀…")를 걷어낸다. 데이터의 유효기간은 `stale_after`로 옮긴다.
- 코드 경로와 패키지명은 현행 명칭만 쓴다. 구 → 신 매핑이 필요하면 `log.md`에 둔다.

문서를 다듬다 아래 신호를 만나면 문서만 고치고 끝내지 말고, 사용자에게 지적하거나 티켓으로 올린다.

- **역할 설명 표가 필요해진다.** 구조가 복잡하다는 신호다. 표는 임시로 두고 구조 단순화 티켓을 제안한다.
- **히스토리 없이는 설명이 안 된다.** 현재 구조가 서사에 기대고 있다는 신호다. 재작성 대상이다.
- **구현이 끝난 PRD가 있다.** 지운다. 교훈과 후속 백로그만 umbrella 문서로 옮기고, `index.md`의 항목을 지우고, `log.md`에 한 줄 남긴다. 설계 의도는 의사 코드 주석으로 이미 코드에 있다.
- **frontmatter와 본문의 담당·상태가 다르다.** 본문 기준으로 frontmatter를 고친다.
