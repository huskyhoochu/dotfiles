# 기획부터 머지까지 — AI 개발 파이프라인 설계

> 날짜: 2026-08-17 (월)
> 전제 인프라: `gem12-private-cloud-plan-2026-08-17.md`
> 상태: 설계. Proxmox 설치 전이라 실행 검증은 하지 않았다.

## 한줄 요약

맥북에서 사람이 고급 모델과 함께 **결정**을 내리고, 서버의 Glimmer가 그 결정을 **구현**한다. 두 층을 물리적으로 분리하는 것이 이 설계의 핵심이다. 구현 층은 flue로 작성한 에이전트가 Forgejo Actions 안에서 돌며, OpenRouter 모델이 리뷰하고, 최대 3회 수정 후 사람이 머지한다.

---

## 1. 두 층으로 나눈다

```text
┌─ 계획 층 (맥북) ────────────────────────────────────────┐
│                                                         │
│  사람 + 고급 모델 (Claude / GPT / Gemini)                │
│  Wayfinder 스킬로 결정 티켓을 지도에 정리                │
│                                                         │
│  산출물: 결정이 끝난 구현 이슈                           │
└─────────────────────────┬───────────────────────────────┘
                          │ 넘김
┌─────────────────────────▼───────────────────────────────┐
│─ 구현 층 (GEM12) ───────────────────────────────────────│
│                                                         │
│  Forgejo Actions → flue 에이전트 → Muse Glimmer 30B      │
│  OpenRouter 모델이 리뷰, 최대 3회 수정                   │
│                                                         │
│  산출물: 리뷰를 거친 PR                                  │
└─────────────────────────┬───────────────────────────────┘
                          │
                     사람이 머지 (맥북)
```

### 왜 나누는가

**Wayfinder는 계획 전용 스킬이다.** 스킬 문서가 "produce decisions, not deliverables"라고 못박고, 구현하고 싶어지는 순간이 지도의 끝이며 넘길 때라고 규정한다. 티켓 네 종류 중 grilling과 prototype은 사람이 반드시 참여해야 하는(HITL) 유형이라 자동화 대상도 아니다.

이 스킬에서 가장 많이 보고된 실패가 **에이전트가 계획 세션 중에 프로덕션 코드를 쓰기 시작하는 것**이다. 계획과 구현이 한 세션에 있으면 경계가 무너진다. 맥북과 서버로 나누면 이 경계가 물리적으로 강제된다.

**분리가 Glimmer에게도 유리하다.** 결정이 전부 이슈에 적힌 뒤에 구현이 시작되므로, 30B 모델이 "이걸 어떻게 할까"를 스스로 판단할 여지가 줄어든다. 판단이 아니라 실행만 맡는다.

---

## 2. 계획 층 — 맥북

Wayfinder로 큰 작업을 지도로 만든다. 이 층은 사람이 주도하므로 자동화하지 않는다.

```text
느슨한 아이디어
   │ /wayfinder
   ▼
지도 이슈 (wayfinder:map 라벨)
   ├── 결정 티켓 (research / prototype / grilling / task)
   └── 아직 못 정한 것 (Not yet specified)
   │
   │ 티켓을 하나씩 해결 — 세션당 하나
   ▼
결정이 다 내려진 상태
   │
   │ 사람이 구현 이슈로 변환
   ▼
구현 이슈 (implement 라벨)
```

**구현 이슈는 지도의 티켓과 다르다.** 지도 티켓은 "무엇을 정할 것인가"이고, 구현 이슈는 "무엇을 만들 것인가"다. 지도가 완성된 뒤 사람이 결정 내용을 근거로 구현 이슈를 작성한다.

구현 이슈에 담아야 하는 것은 다음과 같다. Glimmer가 판단할 여지를 남기지 않는 것이 목적이다.

- 무엇을 바꿀지 — 파일 경로 수준까지
- 왜 그렇게 하는지 — 지도의 결정 티켓 링크
- 완료 조건 — 통과해야 할 테스트나 확인 방법
- 건드리지 말 것 — 범위 밖 영역

---

## 3. 구현 층 — 서버

### 전체 흐름

```text
구현 이슈에 implement 라벨이 붙음
   │
   ▼
Forgejo Actions 기동 (ci-lxc)
   │
   │  flue run implement
   │
   ├─ 1회차 ──────────────────────────────┐
   │  Glimmer 가 코드 작성 → PR 생성       │
   │            ▼                          │
   │  OpenRouter 모델이 리뷰               │
   │            ▼                          │
   │  지적 사항 있음? ─ 예 ─→ Glimmer 수정 │
   │            │                          │
   │            아니오                     │
   └────────────┼──────────────────────────┘
                │           (최대 3회 반복)
                ▼
        PR에 review-passed 라벨
                │
                ▼
        사람이 맥북에서 검토 후 머지
```

### 3회 제한

무한 루프를 막는 장치다. 3회를 넘기면 `needs-human` 라벨을 붙이고 멈춘다. 30B 모델이 스스로 못 푸는 문제를 계속 시도하게 두면 GPU 시간만 소모한다.

## 4. 구성 요소

### Glimmer 서버 — 바인드 주소를 바꿔야 한다

현재 `run-muse-glimmer-server.sh`는 `--host 127.0.0.1`로 뜬다. 데스크톱에서 혼자 쓸 때는 맞지만, **CI가 다른 컨테이너에서 호출하므로 사설망 주소로 바꿔야 한다.**

```text
ai-lxc (10.10.10.14)          ci-lxc (10.10.10.12)
  llama.cpp                     Forgejo Runner
  --host 10.10.10.14   ◄────────  pi --provider muse-glimmer
  --port 8081                     baseUrl: http://10.10.10.14:8081/v1
```

NAT 브리지 내부라 외부에 노출되지 않는다. 서버 전환 시 이 스크립트를 systemd 서비스로 옮기면서 함께 고친다.

`pi`의 `models.json`에서도 `baseUrl`을 컨테이너 주소로 바꾼 프로파일이 필요하다. 맥북용(로컬 접속)과 CI용(사설망 접속)을 따로 둔다.

### GPU 직렬화 — 반드시 필요하다

Glimmer는 VRAM 24560MiB 중 21734MiB를 점유한다. **CI 작업 두 개가 동시에 Glimmer를 부르면 두 번째가 실패하거나 첫 번째를 밀어낸다.**

Forgejo Actions의 concurrency 그룹으로 직렬화한다.

```yaml
concurrency:
  group: glimmer-gpu
  cancel-in-progress: false
```

`cancel-in-progress: false`가 중요하다. 진행 중인 작업을 죽이지 않고 큐에 세운다.

### 리뷰 모델 — OpenRouter

리뷰는 Glimmer가 아닌 다른 모델이 해야 의미가 있다. 같은 모델이 자기 코드를 보면 같은 맹점을 반복한다.

`pi`의 zenmux 프로바이더를 쓴다. 이미 `models.json`에 설정돼 있다. 리뷰는 코드를 쓰지 않고 읽기만 하므로 `--no-tools`나 읽기 전용 도구만 허용해 사고를 막는다.

### 오케스트레이션 — flue를 쓴다

파이프라인을 조립하는 방법은 둘이다. Forgejo Actions의 YAML에서 `pi -p`를 부르고 출력을 파싱하는 방식과, **flue로 TypeScript를 쓰는 방식**이다. 후자를 택한다.

flue는 pi 팀이 만든 에이전트 하네스 프레임워크다. 문서가 "Claude Code인데 100% 헤드리스하고 프로그래밍 가능한 것"이라고 설명하며, 사람이 조작하는 것을 전제하지 않는다. **pi 위에서 돈다** — 즉 이미 쓰고 있는 하네스를 프로그래밍 가능한 형태로 감싼 것이다.

flue를 쓰는 이유는 셋이다.

**첫째, 결과가 스키마로 검증된다.** `pi --mode json`도 JSON을 주지만 구조가 보장되지 않아 YAML에서 파싱하다 깨진다. flue는 valibot 스키마를 강제하고 모델이 형식을 어기면 재시도한다. **30B 모델을 쓸 때 이 차이가 크다.**

```ts
const result = await session.skill('implement', {
  args: { issueNumber },
  commands: [gh],
  result: v.object({
    filesChanged: v.array(v.string()),
    testsPassed: v.boolean(),
    summary: v.string(),
  }),
});

if (!result.testsPassed) { /* 수정 회차로 */ }
```

**둘째, 시크릿이 에이전트에 노출되지 않는다.** `defineCommand`가 토큰을 명령에 묶어 넘기므로 에이전트는 토큰 값을 보지 못한다.

```ts
const gh = defineCommand('gh', { env: { FORGEJO_TOKEN: process.env.FORGEJO_TOKEN } });
```

**셋째, 3회 루프가 TypeScript 제어문이다.** 조건 분기를 YAML로 짜는 것보다 `for` 루프가 명확하고, 회차마다 다른 모델을 지정하기도 쉽다.

flue는 CI 실행을 이미 상정하고 있다. `sandbox: 'local'`은 호스트 파일시스템을 마운트해 저장소가 체크아웃된 CI 환경에 맞춘 모드이고, `triggers = {}`로 두면 HTTP 엔드포인트 없이 `flue run <에이전트>`로만 돈다.

### Glimmer를 flue에 등록한다

flue의 기본 모델 카탈로그는 클라우드 모델만 담고 있다. 로컬 모델은 **커스텀 프로바이더로 직접 등록**한다. 문서가 "a local model, a proxy, a brand-new release"를 등록 대상으로 명시한다.

**등록할 때 `reasoning` 메타데이터를 빠뜨리지 않는다.** 문서에 경고가 있다 — 커스텀 프로바이더에 이 값이 없으면 `thinkingLevel`이 **오류 없이 조용히 무시된다.** Glimmer는 reasoning 모델이고 현재 `pi`의 `models.json`에도 `"reasoning": true`로 등록돼 있으므로, flue 쪽에도 같은 값을 넣어야 한다.

### 긴 루프의 컨텍스트 관리

Glimmer의 컨텍스트는 128k인데 3회 수정 루프를 돌면 대화가 길어진다. flue는 한도에 가까워지면 오래된 이력을 요약으로 접고 최근 대화를 남기는 **compaction**을 자동으로 수행한다.

```ts
useModel('local/muse-glimmer', {
  thinkingLevel: 'high',
  compaction: {
    keepRecentTokens: 16000,
    model: 'zenmux/저렴한-모델',   // 요약은 값싼 모델에 맡긴다
  },
});
```

요약까지 Glimmer가 하면 GPU 시간을 낭비하므로 `compaction.model`로 넘긴다.

## 5. 실현 가능성 판단

| 단계 | 판단 | 근거 |
|---|---|---|
| 맥북 기획 → 이슈 | 확실 | 사람이 한다 |
| 이슈 → Glimmer 구현 | **여기가 관건** | 아래 참조 |
| PR 생성 | 확실 | Forgejo API |
| OpenRouter 리뷰 | 확실 | 읽기만 하므로 난도가 낮다 |
| 리뷰 → 수정 루프 | 확실 | 워크플로 YAML의 조건 분기 |
| 사람 검토 후 머지 | 확실 | Forgejo UI |

### 관건은 Glimmer의 완주율이다

**Glimmer는 이 장비에서 작동이 확인된 유일한 로컬 모델이다.** 대안이 없으므로 완주율이 곧 파이프라인의 성패다. Qwen3-Coder-Next 80B는 CPU 오프로드 탓에 17 tok/s로 떨어져 실용 범위 밖이었다.

30B 모델이 "이슈 읽기 → 코드베이스 탐색 → 파일 수정 → 테스트 실행 → 보고"를 자율로 끝내려면 도구 호출을 수십 번 정확히 해야 한다. 한 번이라도 잘못된 JSON을 뱉거나 엉뚱한 파일을 고치면 그 회차는 버려진다.

유리한 근거가 하나 있다. `run-muse-glimmer-server.sh` 주석의 실측 기록에 **"툴 호출처럼 정형화된 출력일수록 DFlash 채택률이 올라 빠름"**이라고 적혀 있다. 도구 호출을 이미 시켜봤고 잘 되더라는 관찰이다.

그래도 성공률을 올리려면 다음을 지킨다.

- **작업을 작게 쪼갠다.** 파일 1~3개 수정 수준으로 시작하고, 완주율을 보고 늘린다
- **이슈에 판단 여지를 남기지 않는다.** 계획 층에서 결정을 끝내는 이유가 이것이다
- **첫 회차 실패를 정상으로 본다.** 리뷰-수정 루프가 있는 이유다

### 완주율이 끝내 나오지 않으면

작업을 최소 단위로 줄여도 Glimmer가 완주하지 못하면, 파이프라인을 접는 대신 **구현 단계만 OpenRouter 유료 모델로 옮긴다.** 계획 층과 구현 층의 분리, 리뷰-수정 루프, flue 오케스트레이션은 모델과 무관하게 그대로 쓴다. `useModel()` 한 줄만 바꾸면 된다.

비용이 들지만 구조를 다시 짤 필요는 없다. 이슈 라벨로 갈라 작은 작업은 Glimmer가, 큰 작업은 유료 모델이 맡는 절충도 가능하다.

### 실패 처리

| 상황 | 처리 |
|---|---|
| Glimmer가 도구 호출을 실패 | 그 회차를 버리고 다음 회차로. 3회 모두 실패하면 `needs-human` |
| PR이 테스트를 통과하지 못함 | 리뷰 단계로 넘기지 않고 바로 수정 회차로 |
| 리뷰 모델이 3회 후에도 지적 | `needs-human` 라벨을 붙이고 멈춤 |
| GPU 메모리 부족 | concurrency 그룹으로 예방. 그래도 나면 재시도 없이 실패 처리 |

## 6. 구축 순서

인프라 구축(`gem12-private-cloud-plan` §8)이 4단계까지 끝난 뒤 시작한다.

1. **Glimmer 바인드 주소 변경** → 검증: ci-lxc에서 `curl 10.10.10.14:8081/v1/models` 응답
2. **`pi`로 먼저 손으로 돌려본다** — 이슈 하나를 골라 `pi -p --provider muse-glimmer` 실행 → 검증: 코드 수정이 말이 되는가. **여기서 Glimmer의 완주율을 처음 확인한다**
3. **flue 프로젝트 생성, Glimmer를 커스텀 프로바이더로 등록** → 검증: `flue run` 으로 간단한 프롬프트가 돌고 `reasoning`이 실제로 전달되는가
4. **구현 에이전트 하나만 작성** → 검증: 이슈 번호를 넘기면 PR이 생성됨
5. **리뷰 에이전트 추가** → 검증: PR에 리뷰 코멘트가 달림
6. **3회 루프 연결** → 검증: 리뷰 지적이 반영된 커밋이 붙고 3회에서 멈춤
7. **Forgejo Actions에 연결** → 검증: 이슈에 라벨을 붙이면 전체가 자동으로 돎

**2번을 건너뛰지 않는다.** flue를 먼저 붙이면 실패했을 때 모델 문제인지 프레임워크 설정 문제인지 구분할 수 없다. `pi`로 맨손 실행이 되는 것을 확인한 뒤 감싼다.

**7번을 마지막에 둔다.** CI 자동화 전까지는 손으로 `flue run`을 돌려 검증할 수 있다.

## 7. 미결 사항

| # | 항목 | 결정 시점 |
|---|---|---|
| 1 | Glimmer의 실제 완주율 — 작업 크기 상한 | §6 2단계 수동 실행 후 |
| 2 | flue 커스텀 프로바이더 등록 방법의 구체적 형식 | §6 3단계 |
| 3 | 리뷰에 쓸 OpenRouter 모델 선정 | §6 5단계 |
| 4 | 구현 이슈 템플릿 형식 | 계획 층을 처음 돌려본 뒤 |
| 5 | 테스트 없는 저장소의 완료 조건 판정 방법 | §6 4단계 |
| 6 | Wayfinder를 Forgejo 이슈 트래커에 맞추는 설정 | 계획 층 시작 시 |
| 7 | flue가 Forgejo API를 어떻게 다루는지 | §6 4단계 |

**6번**은 확인이 필요하다. Wayfinder는 트래커별 설정 문서를 요구하며 기본값은 로컬 마크다운이다. Forgejo용 설정이 있는지, 없으면 직접 써야 하는지 봐야 한다.

**7번**은 flue 예제가 GitHub의 `gh` CLI를 쓴다는 점에서 나온다. Forgejo는 `gh`가 아니라 자체 API나 `tea` CLI를 쓰므로, `defineCommand`로 무엇을 감쌀지 정해야 한다. Forgejo API가 GitHub와 상당 부분 호환되므로 `gh` 를 `--hostname` 으로 돌릴 수 있는지도 확인 대상이다.

**flue는 실험 단계다.** README가 "Experimental — APIs may change"라고 명시한다. 버전을 고정하고, 업그레이드는 파이프라인이 돌아가는 것을 확인한 뒤에 한다.
